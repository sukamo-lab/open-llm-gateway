# Contributing

Thank you for your interest in LLM Gateway.

## Current contribution policy

The project is currently maintained under a controlled-contribution model. Public bug reports, documentation feedback, feature proposals, and security reports are welcome. Unsolicited pull requests are not accepted at this stage.

Before writing code, open an issue describing the proposed change and wait for explicit written approval from a maintainer. A maintainer may invite a pull request after scope, design, and ownership are agreed. Pull requests without prior approval may be closed without review so the maintainers can keep the architecture and release plan coherent.

Automated dependency-update pull requests created by repository automation configured by the maintainers are pre-authorized and are reviewed under the normal security and CI requirements.

Approval to discuss or investigate an issue is not approval to submit code. Approval applies only to the scope stated by the maintainer and may be withdrawn if project priorities or security constraints change.

## Approved contributions

When a maintainer invites a contribution:

1. Branch from the requested revision and keep the change narrowly scoped.
2. Add or update deterministic tests and user-facing documentation.
3. Run the commands in `docs/DEVELOPMENT.md`.
4. Do not include credentials, customer data, prompts, provider responses, generated secrets, or local configuration.
5. Explain compatibility, migration, security, and operational effects in the pull request.
6. Follow the Code of Conduct and respond to review feedback.

By intentionally submitting a contribution for inclusion, you agree that it is provided under the Apache License 2.0 as described in Section 5 of that license. You represent that you have the right to submit it.

Maintainers may decline, defer, redesign, or close a proposed contribution. There is no guarantee of review, merge, roadmap inclusion, or release timing.

## Issues and feature proposals

Search existing issues before opening a new one. Provide a minimal reproduction for bugs and describe the user problem—not only a preferred implementation—for feature requests. Do not disclose security vulnerabilities in public issues; follow `SECURITY.md`.
